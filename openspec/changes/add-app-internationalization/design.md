## Context

BeatMeter 是一个 Expo + React Native + TypeScript 应用，当前主要用户可见文本散落在组件文件和常量文件中，以硬编码中文为主。现有设置通过 `useSettings` 与 AsyncStorage 持久化，因此语言偏好天然适合沿用同一持久化通道。

这次变更是一次跨模块改动：既涉及 UI 文案来源，也涉及系统语言检测、用户偏好解析、设置面板交互和默认兜底行为。为避免后续新增文案继续回到硬编码模式，需要先建立统一的本地化访问层。

## Goals / Non-Goals

**Goals:**
- 建立应用级中英文国际化机制。
- 支持三种语言偏好：`system`、`zh`、`en`。
- 保证用户手动选择优先于系统语言。
- 在设置面板中提供语言切换入口，并在切换后立即更新界面。
- 让主要用户可见文本通过统一翻译 key 获取，而不是继续在组件中硬编码。

**Non-Goals:**
- 不支持中文、英文以外的语言。
- 不处理 RTL 布局适配。
- 不本地化版本号、BPM 数值、用户导入的文件名。
- 不改变现有节拍器播放、音频或持久化的业务行为。

## Decisions

### 1. 使用轻量级本地化结构，而非引入重型国际化框架
采用适合 Expo + TypeScript 的轻量方案：本地翻译资源 + 共享 i18n 访问层 + 系统语言解析。

**Rationale:**
- 当前语言数量少，仅中英两种。
- 项目规模较小，避免为简单需求引入复杂依赖和额外运行时开销。
- 更容易在现有组件结构中渐进替换硬编码文案。

**Alternatives considered:**
- `react-i18next`：能力强，但对当前需求偏重。
- 完全手写散落式映射：初期快，但后续维护和一致性差。

### 2. 翻译资源使用 TypeScript 模块管理
翻译资源应按语言拆分，并通过 TypeScript 导出统一对象。

**Rationale:**
- 与现有 TypeScript 项目风格一致。
- 更容易做 key 对齐和静态检查。
- 适合管理预设名称、音效描述等结构化文本。

**Alternatives considered:**
- JSON 文件：更通用，但类型约束较弱。

### 3. 语言选择入口放在 Settings 面板
语言设置作为全局偏好配置，放入现有 Settings 面板，而不是主界面。

**Rationale:**
- 符合“全局设置放在设置面板”的用户心智。
- 不增加主界面操作负担。
- 可与音效、触觉、音量等偏好配置保持一致。

### 4. 解析顺序固定为“用户偏好优先，系统语言次之”
最终显示语言按以下顺序决定：
1. 用户手动选择 `zh` 或 `en` 时，始终使用该语言。
2. 用户选择 `system` 时，解析当前系统语言。
3. 若系统语言不在支持范围内，则回退到英文。

**Rationale:**
- 满足用户明确的产品预期。
- 规则简单、稳定、容易测试。

### 5. 翻译覆盖范围应包含结构化常量文案
不仅组件内按钮和标题需要国际化，预设名称/描述、音效名称/描述也必须纳入统一翻译机制。

**Rationale:**
- 这些文本同样直接面向用户。
- 如果保留在常量中硬编码中文，会形成体验割裂。

## Risks / Trade-offs

- [Risk] 现有文本散落在多个组件和常量文件中，容易遗漏。 → Mitigation: 在 spec 中明确翻译覆盖范围，并在任务中列出逐项替换。
- [Risk] 切换语言时如果组件继续直接引用旧常量，界面可能部分不刷新。 → Mitigation: 通过统一的翻译访问层生成展示文本，避免直接消费硬编码 label。
- [Risk] 系统语言解析在不同平台返回格式可能不同。 → Mitigation: 将 locale 归一化，只识别 `zh` / `en`，其余统一回退英文。
- [Trade-off] 轻量方案扩展到更多语言时需要手动维护 key。 → Mitigation: 当前以两种语言为目标，后续如范围扩大再评估更完整框架。

## Migration Plan

1. 新增本地化资源与共享访问层。
2. 扩展设置持久化结构，加入语言偏好字段，默认值为 `system`。
3. 在设置面板增加语言切换 UI。
4. 将已有硬编码文案分批替换为翻译 key。
5. 验证切换即时生效、重启后持久化生效，以及系统语言回退策略。

回滚策略：若本地化改动引发严重显示问题，可回退到变更前版本；因为该变更不涉及数据迁移，仅新增可忽略的设置字段，回滚风险较低。

## Open Questions

- 设置面板中的语言选择控件最终采用分段选择器还是单选列表，可在实现时依据现有 UI 风格确定。
- 如果未来增加更多页面或通知能力，需要把相同 key 命名规范延续到新增文案中。
