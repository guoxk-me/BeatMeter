## Context

当前仓库是 Expo + React Native 的单应用项目，现有能力集中于节拍器播放、BPM 调整、设置持久化与自定义声音导入。v2.0.0 需要在不重构整体技术栈的前提下，引入健身指导信息架构、训练内容浏览、轻量训练时长记录、品牌升级和关于页，同时保证节拍器主流程不退化。

项目约束包括：
- 当前没有后端服务与账号体系，新增数据应继续采用本地存储
- 暂无 AI 图像或视频 API，因此动作媒体能力需使用本地预置图片、封面图或静态占位视频条目替代
- 仓库未配置自动化测试，设计必须支持清晰的手动验收路径

## Goals / Non-Goals

**Goals:**
- 在现有应用中增加“节拍器 / 健身指导”双模块入口
- 以本地静态内容驱动训练分类、动作详情、器械说明和占位媒体展示
- 新增本地训练时长记录，保存最近训练结果与基础偏好
- 完成应用内品牌命名更新、关于页与外部反馈入口
- 在模块切换后保持节拍器播放控制、设置与视觉反馈稳定

**Non-Goals:**
- 不引入云同步、登录系统或远程内容平台
- 不接入真实 AI 图像生成、视频生成或审核服务
- 不实现完整训练计划系统、课程系统或长期训练统计
- 不在本次强制修改包名、商店主体或发布渠道配置

## Decisions

### 1. 采用单应用内双模块导航，而非拆分子应用或深层路由重构
- 方案：继续以现有 `App.tsx` 为应用壳，新增模块级导航状态与对应页面组件
- 原因：当前项目规模较小，直接扩展应用壳最省成本，也更利于保护节拍器已有逻辑
- 备选方案：引入全新的导航架构或多包拆分；放弃原因是改动面过大，且对当前 MVP 无明显收益

### 2. 健身指导内容使用本地结构化数据源
- 方案：新增 `src/constants` 或 `src/data` 下的结构化内容文件，描述分类、动作、器械与占位媒体元数据
- 原因：无需后端即可落地，便于后续替换为远程配置
- 备选方案：直接把内容散落在组件内；放弃原因是可维护性差，后续难扩展

### 3. 训练时长记录仅保存本地最近记录与基础历史
- 方案：在现有设置持久化模式基础上扩展健身记录字段，保存最近一次训练和有限条目历史
- 原因：满足 MVP 记录诉求，同时不引入复杂统计与同步逻辑
- 备选方案：只保存内存态；放弃原因是无法满足重启后可读取的需求

### 4. AI 图和视频需求采用预置占位素材与文案降级
- 方案：动作详情页优先展示本地预置图片；视频先使用封面、说明文案或“即将提供”占位块，不暴露不可用的 AI 生成功能
- 原因：用户已明确当前没有相关 API，应该以可交付替代方案满足浏览和说明需求
- 备选方案：保留不可用入口；放弃原因是会制造空功能与误导预期

### 5. 品牌更名限制在应用内文案与界面露出
- 方案：统一抽取应用名称常量，替换首页、关于页、标题等主要文案，暂不改包名
- 原因：降低发布与迁移风险，并允许后续单独处理商店级变更
- 备选方案：同时修改包名与所有发布配置；放弃原因是超出本次实施边界

## Risks / Trade-offs

- [训练内容规模上升导致 UI 过重] → 先限制为胸、肩、背、腿四类和高频器械，采用可扩展数据结构
- [本地静态内容后续维护成本增加] → 将内容与 UI 解耦，后续可替换成远程数据源
- [模块切换影响节拍器状态] → 保持节拍器 hook 独立，导航切换只改变展示层，不主动重置音频状态
- [预置媒体素材不足以满足“AI 生成”期待] → 在文案中明确本版本提供标准示意图与占位视频，避免承诺未实现能力
- [关于页外链或反馈方式失效] → 提供兜底文案和可替换配置项

## Migration Plan

1. 新增双模块壳层与健身指导页面骨架，但不移除原节拍器主能力
2. 引入健身内容数据、动作与器械详情组件、训练计时与存储逻辑
3. 接入品牌名称常量、关于页和反馈入口配置
4. 用预置素材替代 AI 图与视频入口，补齐空态和错误态文案
5. 手动验证模块切换、训练记录持久化、节拍器基本交互与关于页跳转
6. 若新模块导致节拍器回归，可通过隐藏健身入口和关于入口回滚到旧壳层，不涉及数据迁移回退

## Open Questions

- 新品牌名称是否已经确定，以及是否需要同步更新图标资源
- 博客入口与反馈地址的正式链接是什么
- 训练记录是否需要保存多条历史，还是仅保留最近一次结果
- 预置图片和占位视频素材将由谁提供，放在哪个资源目录
